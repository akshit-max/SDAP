> **Status**: Pending live PostgreSQL verification before tag is applied.
> **Branch**: `feature/organizations`

## Summary

This release establishes the complete secure foundation for the SDAP platform. It ships a production-hardened authentication system, a full organization and membership model, a policy-based RBAC layer, and a verified, stable test suite. All architectural decisions are documented in ADR-001 through ADR-005. No new features should be added until Phase 4 (Vault).

## New Features

### Phase 1 — Authentication
- **Registration** (`POST /api/v1/auth/register`) — Argon2id password hashing, duplicate email detection.
- **Login** (`POST /api/v1/auth/login`) — RS256 JWT access token + SHA-256 hashed refresh token. Generic errors prevent user enumeration.
- **Token Refresh** (`POST /api/v1/auth/refresh`) — Atomic refresh token rotation within a database transaction. Token family tracking.
- **Replay Detection** — Consuming a previously-rotated token revokes the entire family and emits a `RefreshReuseDetectedEvent`.
- **Logout** (`POST /api/v1/auth/logout`) — Revokes the current refresh token by hash.
- **Disabled User Guard** — Inactive or soft-deleted users are rejected at login.

### Phase 2 — Organizations
- **Organization CRUD** — Create, read (single + list), update. Slug auto-generated from name. Uniqueness guaranteed.
- **Automatic Ownership** — Creator is immediately added as `OWNER` member in a single transaction.
- **Organization Limit** — `MAX_ORGS_PER_USER` enforced at creation (configurable in `@repo/config`).
- **Member Invitation** (`POST /api/v1/organizations/:id/invites`) — SHA-256 hashed invitation token, 7-day expiry, re-invite upserts token. Email validated via `CreateInvitationSchema`.
- **Invite Acceptance** (`POST /api/v1/organizations/invites/:token/accept`) — Validates token, status, expiry, and email match. Atomic DB transaction.
- **Domain Events** — `OrganizationCreatedEvent`, `MemberInvitedEvent`, `InvitationAcceptedEvent` emitted via `EventEmitter2`.

### Phase 3 — RBAC
- **Permission Registry** (`@repo/types/permissions.ts`) — Centralized, typed constants. No string literals in business logic.
- **`@RequirePermissions()` decorator** — Declares required permissions per endpoint.
- **`@OrganizationContext()` decorator** — Explicitly declares which route param holds the organization ID. Phase 4-safe (will not confuse `/vaults/:id` with an org ID).
- **`PermissionsGuard`** — Intercepts all protected routes, delegates to the policy chain.
- **`PolicyResolver`** — Resolves `{ userId, organizationId }` using the `@OrganizationContext` declaration. Never guesses params.
- **`MembershipResolver`** — Fetches the caller's active membership record for the resolved organization.
- **`PermissionEvaluator`** — Evaluates permission matrix (OWNER > ADMIN > MEMBER) in memory. Zero DB calls.
- **`AuthorizationService`** — Orchestrates the chain. Exported for use in Phase 4+ guards.

### Phase 3.5 — Stabilization
- **Security headers** via `helmet()` — removes `X-Powered-By`, sets CSP, HSTS, `X-Frame-Options`, and more.
- **CORS** configured with `CORS_ORIGIN` env var (comma-separated). Defaults to `localhost:3000`.
- **`GlobalExceptionFilter`** — Structured error responses `{ success, statusCode, code, message, path, timestamp }`. Never leaks stack traces.
- **Request body size limit** — 1MB cap on JSON and URL-encoded bodies.
- **`GET /health/ready`** — Deep readiness check: PostgreSQL, Redis, JWT keys loaded, env vars validated.
- **ESLint v9** — Flat config operational, `eslint-plugin-prettier` installed, rules tuned for NestJS patterns.
- **Test suite** — All 7 suites, 31 tests passing with proper NestJS mock patterns.

### Infrastructure
- **Docker Compose** — Postgres 15, Redis 7, pgAdmin (optional `--profile tools`)
- **GitHub Actions CI** — 5 independent parallel jobs: `lint`, `typecheck`, `test`, `build`, `prisma`
- **Husky + lint-staged** — Prettier runs on every commit. ESLint available as `npm run lint`.
- **Seed script** — Owner, Admin, Member users + Pending Invitation in a single idempotent run.
- **`check-types`** — `tsc --noEmit` added to `apps/api`. Covered by `turbo run check-types`.

## Database Changes

### New Tables
| Table | Purpose |
|:---|:---|
| `User` | Identity records. `isActive`, `deletedAt` for soft delete. |
| `RefreshToken` | Per-device token tracking with family-based replay detection. |
| `Organization` | Tenant record. Auto-slug, soft delete. |
| `OrganizationMember` | Membership link. Composite unique `(organizationId, userId)`. |
| `OrganizationInvitation` | Hashed invitation tokens with status enum and expiry. |

### New Enums
| Enum | Values |
|:---|:---|
| `MembershipRole` | `OWNER`, `ADMIN`, `MEMBER` |
| `InvitationStatus` | `PENDING`, `ACCEPTED`, `REVOKED`, `EXPIRED` |

### Indexes Added
| Table | Index | Rationale |
|:---|:---|:---|
| `RefreshToken` | `@@index([userId])` | Revoke all tokens for a user |
| `RefreshToken` | `@@index([familyId])` | Replay detection — family revocation |
| `OrganizationMember` | `@@index([userId])` | List all orgs a user belongs to |
| `OrganizationMember` | `@@index([organizationId])` | List all members of an org (every auth request) |
| `OrganizationInvitation` | `@@index([tokenHash])` | Token acceptance lookup |

## Security Improvements

| Area | Detail |
|:---|:---|
| Passwords | Argon2id — `memoryCost: 65536`, `timeCost: 3`, `parallelism: 1` |
| JWT signing | RS256 asymmetric — private key never exposed to clients |
| Refresh tokens | SHA-256 hash stored — raw token never persisted in DB |
| Token rotation | Atomic transaction — no partial state possible |
| Replay detection | Family revocation on reuse — all sibling tokens invalidated |
| User enumeration | Generic `Invalid credentials` on login — no field-level specificity |
| HTTP headers | `helmet()` — 11 security headers on every response |
| CORS | Origin whitelist via `CORS_ORIGIN` env var |
| Body limits | 1MB cap — prevents oversized payload attacks |
| Exception leakage | `GlobalExceptionFilter` — structured response, no internal stack traces |
| Key management | Keys loaded from env (`JWT_PRIVATE_KEY` / `JWT_PUBLIC_KEY`) or `keys/` dir — never auto-generated |

## Next Milestone — Phase 4: Vault

The Vault is the core business domain of SDAP.

**Scope:**
- Encrypted secret storage (AES-256-GCM or libsodium `secretbox`)
- Immutable secret versioning — every write creates a new version record
- `VaultAccess` — scoped permission grants to organization members
- Time-bounded access sessions for credential retrieval
- RBAC integration using `@OrganizationContext` + `@RequirePermissions`

**Hard constraints:**
- Encryption key never stored in the database
- Secret plaintext never appears in logs or error messages
- All access events emitted (ready for Phase 7 Audit)
- No new infrastructure — only the `VaultModule` and its DB models
