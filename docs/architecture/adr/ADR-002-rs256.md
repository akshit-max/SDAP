# ADR 002: JWT Authentication Strategy (RS256)

## Status
Accepted

## Context
We need a robust, stateless authentication mechanism that allows various clients (web app, browser extension) to authenticate. Security is paramount, and the tokens will be used to grant access to a credential vault and temporary integration sessions.

## Decision
We will use **JSON Web Tokens (JWT)** signed with the **RS256** asymmetric algorithm, combined with **Refresh Token Rotation**.

## Rationale
- **Asymmetric Encryption (RS256)**: By using a private key to sign the JWT and a public key to verify it, we can distribute the public key to other services (or the Next.js frontend, or future microservices) so they can verify token authenticity independently without needing to call the API or share a secret.
- **Stateless Verification**: The API doesn't need to hit the database for every request to verify a session, reducing latency and database load.
- **Refresh Token Rotation**: Given the 15-minute short TTL of access tokens, refresh tokens allow persistent sessions. Rotating them on every use ensures that if a refresh token is stolen, reuse of the old token immediately invalidates the entire token family.

## Consequences
- The platform needs secure storage and provisioning of the RSA key pair.
- The Next.js frontend will need to handle token refresh logic seamlessly.
- We need to maintain a stateful `refresh_tokens` table to track families and revocation.
