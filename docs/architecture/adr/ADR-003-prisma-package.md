# ADR 003: Shared Prisma Package

## Status
Accepted

## Context
The platform requires a centralized database schema for NextJS (`apps/web`), NestJS (`apps/api`), and potentially future services. We need to decide where the Prisma schema and generated client should live.

## Decision
The Prisma schema and generated PrismaClient will be located in a dedicated internal package: `packages/db`. 

## Rationale
- **Single Source of Truth**: Having one schema prevents drift between the frontend and backend.
- **Shared Types**: Both `apps/api` and `apps/web` can import the exact same TypeScript types generated by Prisma, making API contracts and full-stack type safety much easier to maintain.
- **Decoupling**: It prevents the backend `apps/api` from strictly owning the database layer, which fits better with a monorepo structure where multiple applications might need direct database access or shared types.

## Consequences
- Prisma commands (`prisma migrate`, `prisma generate`) must be run from `packages/db`.
- The `packages/db` package must be included in the dependencies of `apps/api` and `apps/web`.
- We need to ensure the Turborepo caching is configured so that when `packages/db` changes, dependent apps are rebuilt.
