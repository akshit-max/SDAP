## Release Summary
This release establishes the core cryptographic boundary of the Secure Delegated Access Platform (SDAP). It introduces Vaults and Secrets with immutable versioning, envelope encryption (AES-256-GCM), soft deletes, and deeply integrated audit event hooks. This release completes Phase 4 of the architectural roadmap and transitions the platform into the Stabilization phase.

## Features Included
- **Authentication:** JWT-based login, validation, and refresh flows.
- **Organizations:** Multi-tenant isolation and organizational context.
- **RBAC:** Centralized permission resolution with org-scoped limits and admin overrides.
- **Vaults (NEW):** Cryptographic storage boundaries (`VAULT_CREATE`, `VAULT_READ`, `VAULT_UPDATE`, `VAULT_DELETE`).
- **Secrets (NEW):** Encrypted key-value storage (`SECRET_CREATE`, `SECRET_READ`, `SECRET_UPDATE`, `SECRET_DELETE`, `SECRET_REVEAL`).
- **Secret Versioning:** Immutable, append-only `SecretVersion` records protecting against history tampering.
- **Audit Events:** Standardized `EventEmitter2` payloads for all critical lifecycle events (creation, rotation, reveal, deletion).

## Architecture Snapshot
- **Core Principle:** Thin controllers, thick services, isolated data access layer.
- **Encryption Model:** Envelope Encryption. The Master Encryption Key (MEK) is injected via environment variables and never persisted. Data Encryption Keys (DEKs) are randomly generated per secret, encrypted by the MEK, and stored alongside the ciphertext.
- **Integrity:** AES-256-GCM with Authenticated Associated Data (AAD). The AAD binds the ciphertext to the exact Organization, Vault, Secret, and Version IDs, preventing ciphertext relocation attacks.

## Known Limitations (Deferred)
- **Delegated Access Sessions:** Will be built in Phase 5.
- **Key Rotation:** The interface is prepared (`KeyMetadata`), but the rotation scheduler and API endpoints are deferred.
- **OpenAPI / Swagger Generation:** API documentation is not yet auto-generated.
- **Audit Ledger Export:** Events are emitted natively but not yet persisted to a searchable, compliance-ready ledger.

## Technical Debt
- **Request Typing:** `req.user` is currently typed as `any` in controllers. A `RequestWithUser` interface should be implemented.
- **Prisma Transactions:** Loose typing (`any`) on interactive transaction client callbacks in `vaults.service.ts`.
- **Frontend Vulnerabilities:** `npm audit` reports 29 high-severity findings in the Next.js/Jest toolchain. These do not affect the backend API but must be updated prior to frontend deployment.
- **Test Linters:** ~134 `no-unsafe-*` warnings exist strictly within `.spec.ts` mock setups.

## Security Notes
- **MEK Isolation:** The MEK (`VAULT_ENCRYPTION_KEY`) must be 32 bytes (Base64) and must **never** be committed to source control or logged.
- **Immutable History:** `SecretVersion` rows rely on a `@@unique([secretId, version])` constraint. Updating an existing version is cryptographically and relationally impossible.
- **Soft Deletes:** Deleting a Vault or Secret populates `deletedAt`. Soft-deleted items will unconditionally reject `SECRET_REVEAL` attempts.

## Migration Notes
- Requires applying the latest Prisma migrations: `npx prisma db push` or `npx prisma migrate deploy`.
- Requires setting `VAULT_ENCRYPTION_KEY` in the environment.
